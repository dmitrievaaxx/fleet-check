# Эталонное решение

Информационная система автотранспортного предприятия по контрактам из `../case/`. Назначение: доказать выполнимость ТЗ, дать проверяющей стороне образец и воспроизвести `truth.json` обоих наборов данных через API. Студенту не выдаётся.

Стек: Python 3.11+, FastAPI, SQLite через стандартный `sqlite3`, без ORM. Внешние зависимости только `fastapi`, `uvicorn`, `python-multipart`.

## Запуск

В контейнерах:

```bash
docker compose up --build
```

Локально:

```bash
python -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
ATP_DB_PATH=./atp.db .venv/bin/uvicorn app.main:app --port 8000
```

Сервис слушает порт 8000. Единственная настройка: переменная `ATP_DB_PATH`, путь к файлу базы. В контейнере база лежит на томе `atp-data`, поэтому переживает `docker compose down` и повторный `up`.

## Проверка

```bash
.venv/bin/python -m pytest tests                       # 16 тестов на граничные случаи правил и импорта
.venv/bin/python verify_truth.py ../datasets/public     # приложение в процессе, временная база
.venv/bin/python verify_truth.py ../datasets/hidden --url http://localhost:8000
```

`verify_truth.py` импортирует набор в порядке контракта, сравнивает счётчики и коды ошибок каждого файла с `truth.json`, повторяет импорт и проверяет идемпотентность через `/health`, затем сравнивает отчёт о нарушениях с ожидаемым по ключу (тип, субъект, связанный объект) и по деталям с допусками, прогоняет фильтр по каждому типу и остальные отчёты в JSON и CSV. Код возврата 0 означает полное совпадение.

## Структура

```
app/
  main.py       роуты, разбор параметров, формат ошибок, CSV-представление отчётов
  db.py         схема SQLite, подключение, ленивая инициализация
  importer.py   декларативные описания шести наборов и импорт в порядке проверок контракта
  domain.py     снимок базы в памяти, сезон, пересечение интервалов, пробег на последнем ТО
  rules.py      девять типов нарушений
  reports.py    пять отчётов
  errors.py     ApiError и единый формат ответа об ошибке
tests/          pytest на мини-наборах из трёх ТС и трёх водителей
verify_truth.py прогон набора данных и сравнение с truth.json
```

## Решения, которые стоит знать

- Даты и времена хранятся строками ISO 8601 фиксированной длины. Сравнение строк совпадает с хронологическим, фильтры по дате работают через `substr`.
- Анализ выполняется при каждом запросе отчёта по снимку базы в памяти. На 10 000 листов отчёт о нарушениях формируется за полсекунды, что укладывается в лимит контракта с запасом. Кэширование не понадобилось.
- Параметры запросов принимаются строками и проверяются вручную, чтобы любая ошибка возвращалась в формате `{"error": ...}` с кодом 400, а не стандартным 422 FastAPI.
- Проверка повтора первичного ключа идёт до проверки уникальности вторичных ключей, как требует контракт после уточнения на этапе генератора.
- Список категорий прав: структура (пустой элемент, повтор) даёт `INVALID_FORMAT`, неизвестная категория даёт `INVALID_VALUE`.

## Замер трудоёмкости

Реализация с нуля по готовым контрактам, включая тесты и прогон обоих наборов: около 5 часов для автора, знакомого с правилами. Для студента, который читает контракты впервые и разбирается с Docker, оценка в 30–40 часов на базовую часть выглядит реалистичной. Самые трудоёмкие места: порядок проверок импорта с идемпотентностью, эпизоды пропущенного ТО и подсчёт дней в отчёте об использовании парка.
